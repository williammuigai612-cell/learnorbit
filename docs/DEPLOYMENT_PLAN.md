## 1. Current architecture

### 1.1 What actually ships

LearnOrbit inherits LearnHouse's **all-in-one container** model. There is no separate web image and API
image in the supported path — the root `Dockerfile` builds *one* image containing all three runtimes plus
an internal nginx:

| Stage | Source | Result |
|---|---|---|
| 1–3 | `apps/web` | Next.js 16 standalone build (`output: 'standalone'`, `next.config.js:90`) |
| 4 | `apps/collab` | Hocuspocus/Yjs server compiled to `dist/` |
| 5 | `apps/api` + stages 1–4 | `python:3.14.6-slim-bookworm` + nodejs 22 + bun + pm2 + nginx |

`docker/start.sh` starts three pm2 processes and nginx in the foreground:

* `learnhouse-web` — `server-wrapper.js` (Next standalone), port **8000**
* `learnhouse-api` — `uv run app.py` → uvicorn, port **9000**
* `learnhouse-collab` — `node dist/index.js`, port **4000**
* `nginx` — port **80**, config from `docker/nginx.conf`

Container env baked in `Dockerfile`: `PORT=8000 LEARNHOUSE_PORT=9000 COLLAB_PORT=4000 HOSTNAME=0.0.0.0
LEARNHOUSE_OSS=true NEXT_PUBLIC_LEARNHOUSE_OSS=true PYTHONDONTWRITEBYTECODE=1`. `EXPOSE 80 9000 4000`.

`ARG LEARNHOUSE_PUBLIC=true` (passed by `.github/workflows/build-community.yaml` and `release.yaml`)
deletes `/app/api/ee` from the image. **This is why the OSS build has no EE hooks** — see §15.

### 1.2 Request path

```
Browser
  │  HTTPS
  ▼
Outer reverse proxy  (Caddy 2-alpine  OR  nginx:alpine)   ← generated by the CLI
  │  HTTP, proxy_pass http://learnhouse-app:80
  ▼
Internal nginx (inside the app container, docker/nginx.conf)
  ├─ /collab            → localhost:4000   Collab (WebSocket, 86400s timeouts)
  ├─ /api/v1            → localhost:9000   FastAPI      (3600s timeouts, large uploads)
  ├─ /api/v1/docs|redoc → localhost:9000   (dev mode only — app.py disables them otherwise)
  ├─ /content           → localhost:9000   FastAPI content router (access-controlled)
  ├─ /api/revalidate    → localhost:8000   Next.js
  ├─ /api/auth          → localhost:8000   Next.js
  └─ /                  → localhost:8000   Next.js
        │
        ▼
   PostgreSQL (pgvector/pgvector:pg16)   Redis (redis:7.2.3-alpine)   content volume / S3
```

Note the browser reaches `/api/v1` **directly through nginx**, bypassing Next.js. The Next.js proxy at
`apps/web/app/api/v1/[...path]/route.ts` exists for the non-container/dev path and forwards all headers
except hop-by-hop ones.

## 2. Production prerequisites

* Docker Engine 20.10+ and Docker Compose 2.0+ (per `docs/content/self-hosting/index.mdx`).
* Node.js 18+ on the host **only** to run `npx learnhouse` (the CLI); it is not a runtime dependency.
* A DNS A/AAAA record pointing at the host, resolvable *before* setup if using Caddy (ACME needs it).
* Outbound 80/443 for ACME and for image pulls from `ghcr.io`.
* **Deployment decision — host sizing.** The repository fixes no CPU/RAM/disk figures. Inputs that
  should drive the choice: `client_max_body_size 6G` in both nginx configs, upload caps up to 5 GB
  (`file_validation.py:200,218`), ffmpeg faststart remuxing runs in-process on upload, and an optional
  in-process HLS transcode consumer. Video ingest is the sizing driver, not request concurrency.
* **Deployment decision — container registry: resolved.** See §12.4. The CLI update path is no longer
  hardcoded to `ghcr.io/learnhouse/app`; the image is a per-deployment `appImage` setting, and LearnOrbit
  releases publish to `ghcr.io/williammuigai612-cell/learnorbit`. What remains is execution, not a
  decision: the first publish and its verification (§16).

### 3.6 Findings — unsafe defaults, gaps, and Git exposure

1. **No `.env.example` exists anywhere in this repository.** The only example file upstream ever had was
   `apps/collab/.env.example`, and it is not in this tree. Operators depend entirely on the CLI wizard.
   **This is the single largest documentation gap for a hand-rolled deployment**, and is why §3.1–3.5
   above are written out in full.
2. **`allowed_regexp` ships as a catch-all** (`config.yaml:44`) that matches any well-formed origin. Its
   own comment says CORS and CSRF are "effectively open unless you scope it". `services/email/utils.py:57`
   independently detects and *ignores* this pattern, which corroborates that the codebase treats the
   default as unscoped. **Scoping it is a mandatory pre-deployment step** (§13, §15).
3. **`.gitignore` gap.** The root `.gitignore` covers `.env`, `.env.local`, and `.env.*.local`, but **not
   `.env.production`**. A file named `apps/web/.env.production` or `./.env.production` would be committable.
   Recommend adding `.env.production` / `.env.*` to `.gitignore`. *(Flagged, not changed — 9F alters no
   configuration.)*
4. **`LEARNHOUSE_INITIAL_ADMIN_PASSWORD` persists in `.env`** after bootstrap. Rotate the admin password
   through the UI after first login and blank the variable.
5. **Redis has no password** in the CLI-generated compose and no `ports:` mapping. Its only protection is
   Docker network isolation. See §5.6.
6. **Values that must differ from development:** `LEARNHOUSE_DEVELOPMENT_MODE=False`,
   `LEARNHOUSE_AUTH_JWT_SECRET_KEY` (never reuse a dev secret), `POSTGRES_PASSWORD`,
   `COLLAB_INTERNAL_KEY`, `NEXTAUTH_SECRET`, every `NEXT_PUBLIC_LEARNHOUSE_*` URL/domain,
   `NEXT_PUBLIC_LEARNHOUSE_HTTPS=True`, and `LEARNHOUSE_ALLOWED_REGEXP`/`ALLOWED_ORIGINS`.

## 4. Database and migrations

### 4.1 Creating the database

In-container: the compose `db` service creates `POSTGRES_DB` on first start with the `pgvector/pgvector:pg16`
image. External/managed: create an empty database and a role, then set
`LEARNHOUSE_SQL_CONNECTION_STRING`. The API executes `CREATE EXTENSION IF NOT EXISTS vector` on startup
(`database.py:387`) and **degrades gracefully with a warning** if the role cannot create extensions — only
RAG/chatbot features are lost, which are not V1 surfaces.

### 4.2 The create_all / Alembic interaction — read this before deploying

`connect_to_db` → `_bootstrap_schema` runs **`SQLModel.metadata.create_all` on every API start**
(`apps/api/src/core/events/database.py:398`), unless `TESTING` is set. This matters more than anything else
in this section:

* `create_all` **creates missing tables** but **never alters existing ones**.
* Therefore a brand-new LearnOrbit *table* (`channelvideo`, `organizationfollow`, `quiz`, `notification`,
  `parentchildlink`, …) appears by itself on first boot.
* But a new *column on an existing table* — `organization.channel_type`, `organization.is_verified`,
  `user.is_parent`, `channelvideo.content_format` — **does not**. Without Alembic the API starts and then
  fails at query time.
* A fresh database bootstrapped this way has **no `alembic_version` row**, so a later `alembic upgrade
  head` would try to re-create existing tables and fail.

The CLI already handles this correctly and is the reason to use it:
`ensureAlembicBaseline` (`apps/cli/src/commands/update-ee.ts:110`) runs `alembic current`; if nothing is
stamped it runs `alembic stamp heads`. `runAlembicUpgrade` then upgrades, and if the upgrade fails with
`already exists`/`DuplicateTable` it falls back to `stamp heads`.

### 4.3 Running migrations

Single head, verified: **`b7e4f1a92c83`** (`add_organization_is_verified`). The three earlier heads
(`c1d2e3f4a5b6`, `d3e4f5a6b7c8`, `n4o5p6q7r8s9`) are joined by `e6f7a8b9c0d1_merge_heads.py`.
80 revision files under `apps/api/migrations/versions/`.

```bash
# Community / all-in-one layout (alembic.ini lives at /app/api in the image)
docker compose exec learnhouse-app sh -c "cd /app/api && uv run alembic upgrade head"
```

`migrations/env.py:23` overrides `alembic.ini`'s hardcoded localhost URL from
`LEARNHOUSE_SQL_CONNECTION_STRING`, so the same command works against an external database.

Unrelated: `apps/api/scripts/migrate.py` is a **data**-migration script for role permissions and org
configs (communities, podcasts, boards, playgrounds) — not a schema tool. Do not substitute it for Alembic.

### 4.4 Deploying a new application version

The CLI's `update` flow (`apps/cli/src/commands/update.ts`), in order:

1. `pg_dump | gzip` → `./backups/db-pre-upgrade-<stamp>.sql.gz`; **aborts if the dump is < 100 bytes**.
2. `ensureAlembicBaseline` — stamp if the DB was create_all-bootstrapped.
3. Rewrite the image tag in `docker-compose.yml`.
4. `migrateContentVolume` — moves uploaded content into the persistent volume if it wasn't already.
5. `docker compose pull` → `down` → `up -d`.
6. `waitForHealth` against `/api/v1/health`.
7. `alembic upgrade heads`.

**Migrations run *after* the new container is already serving traffic.** For LearnOrbit's migration set
that is safe (§4.6), but it is not a general guarantee — any future migration that is *not* purely
additive would be applied to a schema the running code already assumes.

### 4.5 Migration failure

`runAlembicUpgrade` returns false, the CLI prints the retry command and points at `./backups/`, and exits 1.
**The application is left running on the new image against the old schema.** The recovery order is: retry
the upgrade manually → if it cannot succeed, roll the image back to the previous tag (§12) → restore the
dump only if the schema was partially altered.

### 4.6 Backward compatibility with rolling deployments

**Every LearnOrbit-authored migration is expand-only and safe for a rolling deploy.** Verified individually:

| Migration | Operation | Rolling-safe? |
|---|---|---|
| `652b0b59778d` channel_type | `add_column` `VARCHAR NOT NULL server_default='SCHOOL'` + index | ✅ old code can still insert |
| `7c8d9e0f1a2b` organizationfollow | `create_table` | ✅ |
| `e77b30b9f1ec` channelvideo | `create_table` | ✅ |
| `a4286436d85d` content_format | `add_column` `NOT NULL server_default='long'` + index | ✅ |
| `d7bab4bd5914` like/save/comment/share | `create_table` ×4 | ✅ |
| `f9a1b2c3d4e5` notification | `create_table` | ✅ |
| `5d1f971f786d` channelresource | `create_table` | ✅ |
| `e8861c4dd570` question | `create_table` | ✅ |
| `685b648bce80` quiz, quizquestion | `create_table` ×2 | ✅ |
| `f4c9a2b7e6d1` quizattempt, quizanswer | `create_table` ×2 | ✅ |
| `72573d15ab51` is_parent | `add_column` `BOOLEAN NOT NULL server_default=false` | ✅ |
| `23f2681a2070` parentchildlink | `create_table` | ✅ |
| `a3c7f92e15b4` channelvideoreport | `create_table` | ✅ |
| `b7e4f1a92c83` is_verified | `add_column` `BOOLEAN NOT NULL server_default='false'` | ✅ |

No `drop_column`, no `alter_column`, no data backfill, no `NOT NULL` without a `server_default` in any of
them. **A migrate-then-deploy ordering is therefore also safe** and is the ordering this plan recommends
(§13) even though the CLI does deploy-then-migrate.

### 4.7 Rollback limitations

Every migration defines a `downgrade()`, and for the additive ones it is a real inverse (`drop_column`,
`drop_table`). **But downgrading destroys data** — `drop_table channelvideo` deletes every video row.
`alembic downgrade` is not a rollback strategy; see §12.2.

## 5. Redis

### 5.1 What it is used for

Confirmed consumers (`grep` over `apps/api/src`, excluding tests): rate limiting
(`services/security/rate_limiting.py`), account lockout (`security/account_lockout.py`), security activity
(`security/activity.py`), analytics cache, orgs cache / invites / usage, email verification, password
reset codes, AI generation state and pack credits, HLS transcode queue (`utils/hls_jobs.py`), AI captions
queue (`utils/caption_jobs.py`), playground/board generators.

### 5.2 Required for startup?

**No.** `core/redis.py::get_redis_client()` returns `None` when the connection string is missing or the
pool cannot be built, and logs at debug level. `startup_app` calls `_reconcile_packs()`, which catches
every exception and logs "Pack reconciliation skipped (non-fatal)". The API boots without Redis.

`docker-entrypoint.sh` *waits* up to 60s for Redis if `LEARNHOUSE_REDIS_CONNECTION_STRING` is set and then
exits 1 — but the all-in-one image runs `docker/start.sh`, not that entrypoint, and `start.sh` waits only
for the database. So in the supported deployment Redis is genuinely optional at boot.

### 5.3 Rate limiting behaviour, and the F2 fail-open

Two different behaviours, deliberately:

* **Auth-side limiters** (`check_login_rate_limit`, signup, refresh, password reset, API-token creation,
  admin provision/lookup) call `get_redis_connection()`, which raises **HTTP 500** when Redis is absent.
  They fail *closed*: no Redis, no login.
* **LearnOrbit engagement limiters** (`check_learnorbit_rate_limit`, `rate_limiting.py:590`) **fail open.**
  On any Redis exception the call returns `(True, window_seconds)`, logs
  `"LearnOrbit rate limiting degraded — Redis unavailable (action=%s)"` at WARNING, and sets a 30-second
  process-local backoff (`LEARNORBIT_REDIS_BACKOFF_SECONDS`) so it stops paying connect timeouts.

Buckets (`LEARNORBIT_RATE_LIMITS`): `reaction_toggle` 120/min, `share_create` 60/min, `comment_write`
20/min, `report_create` 10/h, `moderation_write` 60/min, `content_write` 60/min, `quiz_attempt_start` 30/h,
`parent_link_write` 10/h. Anonymous callers get an IP-keyed bucket capped at 20.

> **Operational implication of F2 — state this in the runbook.**
> While Redis is unreachable, **all LearnOrbit engagement rate limits are off**: comments, likes, saves,
> follows, shares, reports, moderation writes, quiz-attempt starts and parent-link requests accept
> unlimited requests. This is a deliberate availability trade recorded in `docs/PROGRESS.md` (F2) — taking
> engagement down whenever the cache tier blinks was judged worse than the abuse the ceiling prevents.
> Ownership checks, RBAC and the DB uniqueness constraints on likes/saves/follows/parent-links **all still
> apply**, so the failure mode is volume, not authorization. **Therefore: alert on the "rate limiting
> degraded" WARNING line, and treat Redis downtime as a security-relevant event, not merely a performance
> one.** A second consequence in the same window: login, signup and password reset return **500**, so the
> practical incident is "logins are down *and* engagement abuse controls are off".

### 5.4 Authentication / session behaviour

Sessions are stateless JWTs, so **existing logins survive a Redis outage**. What does not survive: new
logins and signups (500), password-reset code issue/consume (codes live in Redis with a 1 h TTL and are
single-use), email verification resend, and account lockout counters.

### 5.5 Persistence

The generated compose runs `redis-server --appendonly yes` with a named volume at `/data`. AOF persistence
is therefore **on by default and should stay on**: password-reset codes, email-verification state and
pack-credit reconciliation state live only in Redis, and losing them mid-flight strands users.
Cache-only data would tolerate a flush; these do not.

### 5.6 Must Redis be private?

**Yes, and it currently has no other protection.** The generated compose sets no `requirepass` and
publishes no `ports:`, so isolation is entirely `learnhouse-network-<id>`. If Redis is ever moved to a
managed/external service, it **must** use TLS + auth in `LEARNHOUSE_REDIS_CONNECTION_STRING`. Note the dev
compose (`.learnhouse/docker-compose.dev.yml`) *does* publish 6379 to the host — never reuse it in
production.

## 6. Storage, files and uploads

* **Location:** `content/`, resolved **relative to the API working directory** — `check_content_directory`
  (`core/events/content.py`) does `os.makedirs("content")`. In the image that is `/app/api/content`.
* **Mode:** `filesystem` (default) or `s3api`, selected by `LEARNHOUSE_CONTENT_DELIVERY_TYPE`. `app.py`
  mounts `content_files_router` for S3 and `local_content_router` otherwise. **Neither serves raw
  `StaticFiles`** — both enforce access control.
* **Required volume:** `learnhouse_content_<id>:/app/api/content`, created by the CLI only when
  `!s3Enabled`. **Without it, every upload is lost on container recreation.** `migrateContentVolume` in
  the update path exists specifically to repair installs that predate this.
* **Access model:** public — org branding/logos, course thumbnails; authenticated — activity content
  (videos, PDFs, blocks) for non-public courses, non-public podcast episodes, and submission files
  (`security/submission_file_access.py`). Path traversal is blocked by
  `_normalize_content_relpath` (double-decode, then reject `..`, leading `/`, NUL) plus an inline realpath
  containment check at each filesystem sink.
* **Size limits** (`security/file_validation.py:194–255`): images 15 MB, video 5 GB, audio 500 MB,
  documents 1 GB, SCORM/zip 5 GB and 2 GB (both additionally bounded by a 500 MB uncompressed zip-bomb
  guard), 50 MB and 100 MB for the remaining categories. Both nginx layers must allow this — they set
  `client_max_body_size 6G`, and the CLI's outer nginx template carries an explicit comment that a lower
  value here 413s the request before it reaches the app.
* **Deployment effect on existing content:** in filesystem mode content is volume-resident and survives
  `docker compose down`/`up` and image changes. It does **not** survive `docker compose down -v` or volume
  deletion. In S3 mode the container is stateless for content.
* **Backups:** see §9 — **`npx learnhouse backup` does not back up the content volume.**

*(The upload system is documented here, not redesigned. No change proposed.)*

### 7.2 Proxy requirements the code depends on

`get_client_ip` (`rate_limiting.py:46`) trusts `X-Forwarded-For`/`X-Real-IP` **only** when the direct peer
is loopback/private. Its own comment states the requirement plainly: **the reverse proxy MUST overwrite,
not append-through, client-supplied `X-Forwarded-For`.** Both bundled nginx configs use
`$proxy_add_x_forwarded_for`, which appends — correct behaviour *given* that the outermost proxy is the
trust boundary. If a third proxy or CDN is added in front, it must strip client-supplied values or IP-based
rate limiting can be bypassed by spoofing.

### 7.3 Mandatory pre-deployment configuration

Because `LEARNHOUSE_ALLOWED_REGEXP` is read by CORS, CSRF *and* email link generation, scoping it is the
single highest-value configuration action:

```
LEARNHOUSE_ALLOWED_REGEXP=^https://(?:[a-z0-9-]+\.)*learnorbit\.example(:\d+)?$
LEARNHOUSE_ALLOWED_ORIGINS=https://learnorbit.example
LEARNHOUSE_FRONTEND_DOMAIN=learnorbit.example
```

*(Illustrative host — substitute the real production domain.)*

## 9. Backup and recovery

### 9.1 What the tooling covers

`npx learnhouse backup` (`apps/cli/src/commands/backup.ts`) runs
`pg_dump -U learnhouse --clean --if-exists learnhouse` and tars the result into
`./backups/<name>.tar.gz`. The pre-upgrade backup in `update-ee.ts:61` uses `pg_dump | gzip` and works for
both the in-container DB and an external one (via a `postgres:17` client sharing the app container's
network namespace), aborting if the dump is under 100 bytes. `npx learnhouse restore` extracts and replays
a dump.

### 9.2 The gap

> **`npx learnhouse backup` backs up PostgreSQL only. The `learnhouse_content_*` volume — every uploaded
> video, PDF and past paper — is not included.**

For LearnOrbit specifically this is the more painful loss: the database holds `ChannelVideo` and
`ChannelResource` *rows* whose files live in the volume. A DB-only restore yields a catalogue of broken
links.

**Required addition to any V1 runbook (filesystem mode):**

```bash
docker run --rm \
  -v learnhouse_content_<deploymentId>:/data:ro \
  -v "$PWD/backups":/backup \
  alpine tar -czf /backup/content-$(date +%Y%m%d-%H%M%S).tar.gz -C /data .
```

In S3 mode this is unnecessary — enable bucket versioning and lifecycle rules instead.

### 9.3 Targets

All of the following are **Deployment decisions** — the repository determines none of them. Suggested V1
starting points, to be confirmed:

| Item | Suggested V1 | Rationale |
|---|---|---|
| PostgreSQL backup frequency | daily, plus the automatic pre-upgrade dump | the pre-upgrade dump already exists and is enforced |
| Content volume backup | daily; weekly full if incremental tooling is added | pairs with the DB so the two restore consistently |
| Retention | 7 daily + 4 weekly | |
| Off-host copy | required | `./backups/` lives on the same host as the data it protects |
| Restore testing | quarterly, into a scratch environment | untested backups are not backups |
| **RPO** | ≤ 24 h | direct consequence of daily dumps; tighten with WAL archiving / a managed DB if unacceptable |
| **RTO** | ≤ 4 h | pull image + restore dump + restore content + `alembic upgrade` |
| Redis recovery | **no backup required** | AOF gives crash recovery. Acceptable loss on total failure: in-flight password-reset codes, verification-resend counters, rate-limit counters, cached analytics. All regenerate. Users retry a reset. **Do not** restore a stale Redis snapshot over a live one — it would resurrect consumed reset codes |

**Recovery priority:** 1. PostgreSQL → 2. content volume → 3. app container → 4. Redis (empty is fine) →
5. TLS/Caddy state (re-issues automatically).

## 10. Deployment strategy

### 10.1 Options against what the repo supports

| Option | Repository support | Verdict |
|---|---|---|
| **Single-server Docker Compose via the LearnHouse CLI** | **First-class.** `apps/cli` generates compose, `.env`, Caddyfile/nginx conf; `setup`/`start`/`stop`/`status`/`logs`/`health`/`doctor`/`backup`/`restore`/`update`/`scale`/`shell` all exist | ✅ **Recommended** |
| Single-server Compose, managed PostgreSQL + managed Redis | Supported: `config.useExternalDb` / `useExternalRedis` omit the local services, and the backup path explicitly handles an external DB. `database.py:105` even detects a connection pooler and drops to `pool_size=5` | ✅ Good upgrade path |
| Separate web / API deployment | **Not supported by the shipped image.** The all-in-one image bundles all three runtimes behind one internal nginx. `apps/web/Dockerfile`, `apps/api/Dockerfile` and `apps/collab/Dockerfile` exist individually but no compose file wires them together, and no CLI path targets them | ❌ Would require new infrastructure |
| Kubernetes | No manifests, no Helm chart, no readiness/liveness split beyond the one endpoint | ❌ Out of scope |
| PaaS (Vercel/Fly/Render) | `fly.toml` and `.flyio/` are `.gitignore`d, i.e. explicitly not tracked | ❌ Not supported |

### 10.2 Recommendation

**Single-server Docker Compose via the LearnHouse CLI, with Caddy for TLS**, moving PostgreSQL to a
managed service when data volume or RPO demands it.

Why:

1. It is the **only path the repository actually automates end to end**, including the two operations most
   likely to go wrong — the Alembic baseline/stamp dance around `create_all` (§4.2) and the content-volume
   migration (§6).
2. **Caddy over nginx**, unambiguously: the nginx template terminates no TLS and performs no HTTP→HTTPS
   redirect (§7.1). Choosing it means building TLS separately, and `secure` cookies then depend on a
   correct `X-Forwarded-Proto` from a proxy you wrote yourself.
3. `tenancy: single` is V1's mode; multi-tenant subdomain routing needs EE and is out of scope.
4. It matches V1's actual shape — one org, one domain, one operator.

Trade-off stated plainly: this is a **single point of failure with downtime during updates**
(`update.ts` does `down` then `up`). For V1 that is acceptable; it is the reason §12 leans on image-tag
rollback rather than blue/green.

## 12. Rollback

**Code rollback and database rollback are different operations with different risk. Do not conflate them.**

### 12.1 Application / image rollback (safe, fast, the primary lever)

```bash
npx learnhouse update --version <previous-version> --no-migrate
```

`--no-migrate` is essential: the goal is old code on the current schema. Because every LearnOrbit migration
is additive with `server_default`s (§4.6), **the previous application version runs correctly against the
newer schema** — the extra columns and tables are simply ignored. This is the rollback path to use.

Manually: edit the `image:` tag in `docker-compose.yml` (`replaceComposeImageTag` does exactly this), then
`docker compose pull && docker compose up -d`.

### 12.2 Database migration rollback (destructive — avoid)

`alembic downgrade <rev>` runs the real inverse: `drop_column`, `drop_table`. **`drop_table channelvideo`
deletes every video row.** Use it only when a migration is known to have corrupted the schema *and* a
restore is worse.

Preferred recovery is the pre-upgrade dump:

```bash
gunzip -c backups/db-pre-upgrade-<stamp>.sql.gz | \
  docker compose exec -T db psql -U learnhouse learnhouse
```

Because the dump is taken with `--clean --if-exists`, this is a replace, not a merge. **It discards every
write made after the dump** — always pair a DB restore with an image rollback to the matching version.

### 12.3 Frontend and configuration rollback

There is no independent frontend rollback: web, API and collab ship in one image, so §12.1 rolls back all
three together. Configuration rollback is `.env` + `docker-compose.yml` + `extra/Caddyfile` — **keep these
three files in version control or in a backup, since the CLI rewrites them in place.** Restoring a
`NEXT_PUBLIC_*` value needs only a container restart (§3.2); it does not need a rebuild.

### 12.4 The LearnOrbit image — resolved

The blocker this section originally recorded (the CLI resolving every deployment's image from a constant
compiled into it, so `npx learnhouse update` on a LearnOrbit install would pull upstream LearnHouse) is
closed. Two changes, in order:

**1. LearnOrbit publishes its own image.** `.github/workflows/release.yaml` builds the existing root
`Dockerfile` for amd64 + arm64 and pushes to `${{ github.repository }}` under `ghcr.io` — that is,
**`ghcr.io/williammuigai612-cell/learnorbit`**. The path is derived, never hardcoded, so it can only ever
resolve to a namespace this repository's own `GITHUB_TOKEN` may write.

* **Release tags are `lo-X.Y.Z`** (`lo-1.0.0`). The namespace is deliberate: the fork inherited 20 tags
  matching upstream's `[0-9]*` pattern and 13 matching `cli-[0-9]*`, and none of them can match `lo-`.
* **Image tags are plain semver** — `lo-1.0.0` publishes `…/learnorbit:1.0.0`. The `lo-` prefix belongs to
  git tagging and never reaches the image.
* **`:latest` is not published.** Production pins an immutable version tag, which is what makes the
  image-tag rollback in §12.1 deterministic. A floating tag would let `docker compose pull` move a
  deployment without anyone choosing to.

**2. The image is a property of the deployment, not of the CLI.** `learnhouse.config.json` gained an
optional `appImage` field holding the image *repository* (no tag):

```json
{
  "deploymentId": "…",
  "appImage": "ghcr.io/williammuigai612-cell/learnorbit",
  "orgSlug": "default"
}
```

* **Set it at install time** with `npx learnhouse setup --image ghcr.io/williammuigai612-cell/learnorbit:1.0.1`.
  The repository half is persisted as `appImage`; the tag half pins the generated `docker-compose.yml`.
  Omitting the tag pins the version this CLI ships (`APP_IMAGE_VERSION` in
  `apps/cli/src/constants.ts`), because this project publishes no `:latest`; a third-party repository
  still falls back to `:latest`. Passing the version explicitly stays the clearest option.
* **`update` reads it back.** With `appImage` set, `npx learnhouse update --to 1.0.1` retags *that*
  repository and never queries or substitutes `ghcr.io/learnhouse/app`. Backup, Alembic baseline,
  migrations, the health gate and rollback semantics are unchanged.
* **Mismatch fails closed.** If `appImage` and the repository in `docker-compose.yml` disagree, the update
  aborts before the backup: nothing is pulled, restarted or migrated, the compose file is not touched, and
  the error names both values. Previously this case silently changed nothing and still reported success.
* **`appImage` is not a secret** — it is a public image path and belongs in version control alongside the
  rest of the deployment config.

**3. Default image resolution is pinned, not discovered.** `resolveAppImage()` used to read
`api.github.com/repos/learnhouse/learnhouse/releases` — upstream's numbering decided what a LearnOrbit
install ran — and fell back to `:latest` on any failure. It now returns `APP_IMAGE`
(`…/learnorbit:${APP_IMAGE_VERSION}`) with no network call at all: since exactly one immutable tag is
published per `lo-X.Y.Z` and no floating tag exists, the version the CLI ships with *is* the answer, and
a lookup could only ever return a tag that was never published. **`APP_IMAGE_VERSION` must be bumped
when a new `lo-` tag is released**, and the tag it names must exist in GHCR before that CLI version is
used to install.

**Backward compatibility:** a config without `appImage` behaves exactly as before — `ghcr.io/learnhouse/app`,
resolved through the release channel. Existing LearnHouse installations are unaffected.

## 13. Deployment procedure

Recommended ordering — **migrate before deploy**, which §4.6 proves safe for LearnOrbit's expand-only
migration set, unlike the CLI's default deploy-then-migrate.

### 13.1 First deployment

1. DNS A/AAAA → host; confirm it resolves (Caddy's ACME challenge depends on it).
2. `npx learnhouse@latest setup` — domain, admin credentials, org name/slug, TLS mode (**choose auto-SSL /
   Caddy**), DB and Redis (in-container or external), email provider, storage mode.
3. **Edit the generated `.env` before first start** and add what the wizard does not write:
   `LEARNHOUSE_ALLOWED_REGEXP` (scoped), `LEARNHOUSE_ALLOWED_ORIGINS`, `LEARNHOUSE_FRONTEND_DOMAIN`,
   `LEARNHOUSE_ENV=production`, and optionally `LEARNHOUSE_SENTRY_DSN`. Confirm
   `LEARNHOUSE_DEVELOPMENT_MODE=False`.
4. Pin the LearnOrbit image at install time — pass `--image ghcr.io/williammuigai612-cell/learnorbit:<version>`
   to `setup` (§12.4). Always include the version: `:latest` is not published.
5. `npx learnhouse start`.
6. First boot performs, in order: `create_all` → `auto_install` (seeds the org and admin because no
   `Organization` row exists) → default-role refresh → pack reconciliation → background consumers.
7. **Stamp Alembic** so future upgrades apply only the delta:
   `docker compose exec learnhouse-app sh -c "cd /app/api && uv run alembic stamp head"`.
8. `npx learnhouse doctor` and `npx learnhouse health`.
9. Run §14 post-deployment verification.
10. Rotate the admin password in the UI; blank `LEARNHOUSE_INITIAL_ADMIN_PASSWORD` in `.env`.

### 13.2 Subsequent deployments

1. `npx learnhouse backup` **plus** the content-volume tar from §9.2.
2. `docker compose exec learnhouse-app sh -c "cd /app/api && uv run alembic upgrade head"` — migrate first.
3. Pull and restart on the new tag (`npx learnhouse update --to <version> --no-migrate` — with `appImage`
   set this retags the LearnOrbit repository and never falls back to upstream, §12.4; or
   `docker compose pull && docker compose up -d` on a manually pinned image).
4. `waitForHealth` / `curl -f https://<domain>/api/v1/health`.
5. §14 smoke checks.

## 15. F3 — CSRF decision

**Decision: config-first. 9F changes no code. Scoping `LEARNHOUSE_ALLOWED_REGEXP` /
`LEARNHOUSE_ALLOWED_ORIGINS` to the production domain becomes a mandatory pre-deployment step; registering
`CSRFProtectionMiddleware` is queued as a separate, later increment with the prerequisites recorded below.**

This supersedes the "register it in 9F" note in `docs/SECURITY_REVIEW.md` § "Recommended fixes before Phase
9F" item 4. That note assumed registration was a one-line change; the analysis below shows it is not.

### 15.1 How authentication actually works

* **Issued where:** `POST /auth/login`, `/auth/login/mfa`, the Google third-party path, and
  `/auth/refresh`. All funnel through `set_auth_cookies` (`routers/auth.py:184`).
* **Cookie- or header-based? Both.** `extract_jwt_from_request` (`security/auth.py:85`) prefers
  `Authorization: Bearer <jwt>` — explicitly *excluding* `Bearer lh_*` API tokens — and **falls back to the
  `LH_access` cookie**. The web client sends `credentials: 'include'` on every request
  (`services/utils/ts/requests.ts:33, 60, 76`), so browser traffic always carries cookies even when a
  Bearer header is present. Tokens are additionally returned in the login response body; the frontend does
  **not** persist them (`SECURITY_REVIEW.md` §37 — nothing in `localStorage`/`sessionStorage`).
* **Cookie flags in production:** `LH_access` (8 h) and `LH_refresh` (30 d), both
  `httponly=True, secure=is_request_secure(request), samesite="lax"`, `domain=None` under
  `tenancy: single`.
* **Which state-changing endpoints depend on cookies:** effectively all of them for browser traffic —
  every LearnOrbit mutation (follows, likes, saves, comments, shares, reports, moderation writes, channel
  content, quiz attempts, parent links) plus every inherited course/org/admin mutation.

### 15.2 The middleware, and why it is unregistered

`src/security/csrf.py::CSRFProtectionMiddleware` validates the `Origin` header (falling back to `Referer`)
on `POST`/`PUT`/`DELETE`/`PATCH`, returning **403** when neither is present or allowed. It exempts, by
design: `Bearer lh_*` API tokens, Stripe `stripe-signature` webhooks, and the `x-internal-key` /
`x-platform-key` service-to-service headers. Regular `Bearer <jwt>` is **deliberately not exempt**, because
`get_current_user` falls back to cookies when the JWT is invalid — so exempting it would let an attacker
send a junk Bearer header to bypass CSRF while the victim's cookies did the real authentication.

It is never registered. `app.py` adds `configure_cors`, `SelectiveGZipMiddleware` and
`register_ee_middlewares(app)` — and the last is a no-op in this build: `is_ee_available()`
(`core/ee_hooks.py:16`) requires both `ee/` and `ee/hooks.py`, and `apps/api/ee` **does not exist in this
checkout** (it is `.gitignore`d as a private overlay) and is deleted from every published image by
`ARG LEARNHOUSE_PUBLIC=true`. `register_ee_middlewares` additionally returns early when `saas_mode` is set.

### 15.3 Why registering it *as-is* would be net-negative

**It would protect nothing.** `_is_origin_allowed` checks `allowed_origins`, then
`compiled_regexp.fullmatch(origin)`. The shipped `allowed_regexp` (`config.yaml:44`) is
`\b((?:https?://)[^\s/$.?#].[^\s]*)\b` — a catch-all that fullmatches **any** well-formed origin, an
attacker's included. The config file's own comment states CORS and CSRF are "effectively open unless you
scope it", and `services/email/utils.py:57` independently detects and ignores this exact pattern as
unscoped. The CLI's generated `.env` never sets `LEARNHOUSE_ALLOWED_REGEXP` or `LEARNHOUSE_ALLOWED_ORIGINS`
(`apps/cli/src/templates/env.ts`), so a real deployment inherits the catch-all.

**And it would break things.** Any state-changing request with neither `Origin` nor `Referer` gets a 403:

* ~~**The test suite:** **475 mutation calls across 53 files**… Near-total suite failure.~~
  **SUPERSEDED — this never applied.** No test file imports `app.py`; there is no `TestClient(` anywhere in
  the suite. Every file builds its own bare `FastAPI()` and drives it through `httpx.ASGITransport`, so no
  mutation call traverses `app.py`'s middleware stack. Verified when the increment landed: the full suite
  is unchanged by registration. The real gap was the inverse — registration had *no* coverage — closed by
  `src/tests/security/test_csrf_app_level.py`.
* **Non-browser JWT clients** — curl, scripts, ops tooling — since only `lh_*` tokens are exempt.
* **Server-side fetches from Next.js** that construct their own requests rather than forwarding browser
  headers. The `/api/v1/[...path]` proxy forwards `Origin` correctly, but the `app/api/billing/*` and
  `app/api/loops/*` route handlers do not.

### 15.4 Is `SameSite=Lax` sufficient?

For the V1 threat model, **it is doing the real work today and is close to sufficient**:

* Lax suppresses cookies on all cross-site `POST`/`PUT`/`PATCH`/`DELETE` — which is every state-changing
  method the API exposes.
* Residual gap (a): cross-site **GET** navigations still send the cookie. No LearnOrbit mutation is exposed
  over GET, so there is no GET-triggered state change to forge.
* Residual gap (b): a *same-site, different-origin* attacker (a hostile subdomain sharing the cookie
  domain) is not stopped by Lax. This requires `tenancy: multi` with a dotted `LEARNHOUSE_COOKIE_DOMAIN` —
  **EE-only, and not the V1 deployment**, which is `tenancy: single` with host-only cookies.

Conclusion: a genuine **defence-in-depth gap**, not an exploitable hole in the V1 single-tenant
configuration.

### 15.5 What 9F does instead

1. **Scoping `LEARNHOUSE_ALLOWED_REGEXP` and `LEARNHOUSE_ALLOWED_ORIGINS` is now a mandatory
   pre-deployment step** (§3.2, §7.3, §13.1 step 3, §16). It scopes **email link generation** and —
   once registered — **CSRF**. **CORRECTION:** it does *not* scope CORS under `tenancy: single`, the V1
   deployment: `get_cors_origin_regex()` builds its regex from `frontend_domain`/`domain` plus localhost
   and only reads `allowed_regexp` in `multi` mode. CORS was already scoped. Since the CSRF increment the
   CLI's generated `.env` sets both variables from the configured domain, so a new install is scoped by
   default.
2. `SameSite=Lax` is documented as the active CSRF control, with its two residual gaps stated (§15.4).
3. Registration is queued as its own increment with explicit prerequisites (§15.6).

### 15.6 The smallest safe change, for the follow-up increment

**IMPLEMENTED.** `app.py` registers the middleware between `configure_cors(app)` and
`register_ee_middlewares(app)`, alongside a `warn_if_origins_unscoped()` startup guard. The prerequisites
below were re-checked against the code first; items 2 and 5 were wrong as written — see §15.3 and the
2026-08-26 entries in `docs/PROGRESS.md`. Item 5's real breaking callers were the auth proxy (login and
refresh), the logout DELETE, 19 payment server actions, and signup — not `app/api/billing/*` or
`app/api/loops/*`, which issue no non-GET to the API.

Original analysis, retained:

```python
# apps/api/app.py — after configure_cors(app), before register_ee_middlewares(app)
from src.security.csrf import CSRFProtectionMiddleware
...
app.add_middleware(CSRFProtectionMiddleware)
```

Prerequisites, all of which must land **in the same increment**:

1. **Scoped `allowed_regexp` in production**, or the middleware is inert (§15.3). Consider also failing
   startup — or logging `CRITICAL` — when `development_mode` is false and `allowed_regexp` is the
   catch-all; `email/utils.py` already has a `_is_scoped_origin_regexp` helper to reuse rather than
   reimplement.
2. **A test-suite strategy** for the 475 mutation calls. Cheapest correct option: a `conftest.py` fixture
   that sets a default `Origin` header on the shared `TestClient`, so tests exercise the middleware
   instead of bypassing it.
3. **Guard against double registration** if `ee/hooks.py` ever appears — EE registers the same middleware,
   and `register_ee_middlewares` is still called.
4. **`saas_mode` interaction** — registering in `app.py` (rather than via the EE hook) means CSRF applies
   even under `LEARNHOUSE_SAAS=true`, where `register_ee_middlewares` currently returns early. Intended,
   but a behaviour change worth naming.
5. **Verify no server-side Next.js mutation path breaks** — audit `app/api/billing/*` and
   `app/api/loops/*`, which build their own fetches rather than forwarding browser headers.
6. **Security tests** asserting a cross-origin POST is rejected and a same-origin POST is accepted, at the
   app level rather than against a bare middleware instance.

## 17. Known limitations of this plan

* **Nothing here was executed.** No deployment, no build, no migration run, no container started. Every
  statement is derived from reading the repository.
* **The venv at `apps/api/.venv` is a Linux venv reached over a Windows UNC path**, so `alembic`, `pytest`
  and `ruff` could not be executed in this session. The single-head result in §4.3 was computed by parsing
  `revision` / `down_revision` across all 80 files and resolving `e6f7a8b9c0d1_merge_heads.py`'s three-way
  merge — **not** by running `alembic heads`. Confirm with `alembic heads` before deploying.
* **Sizing, alerting thresholds, retention, RPO/RTO and the registry choice are Deployment decisions**, not
  repository facts, and are labelled as such.
* **The multi-tenancy verification gap persists** (`CLAUDE.md`, `SECURITY_REVIEW.md` §6/§3.5): browser-level
  cross-org isolation cannot be exercised locally because `tenancy: single` collapses org routing and
  `multi` is hard-rejected on localhost domains. Irrelevant to V1's single-tenant deployment, but it means
  the multi-tenant cookie-domain reasoning in §15.4(b) is analytical, not tested.
